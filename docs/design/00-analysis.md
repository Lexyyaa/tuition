### S-3

> 학원 원장이 강좌와 수강생을 관리하고, 매달 학부모에게 원비 고지서를 알림톡으로 발송하며, 납부를 관리하는 서비스의 백엔드를 구현합니다.

- 명시되지 않은 것
  - 학부모와 수강생의 관계 모델
    - 학부모 한 명에 수강생 여러 명이 가능한지
    - 수강생 한 명에 학부모 여러 명이 가능한지
  - 학부모의 전화번호를 어디에 두는지
  - 고지서의 단위
    - 수강 등록 1건당 1장인지
    - 학부모 1명당 월 1장으로 합산하는지
  - "원장"이 API 호출 주체인지, 별도 사용자 개념인지
- 깨지는 시나리오
  - 한 학부모에게 자녀 3명 × 강좌 2개 = 6장의 고지서가 같은 날 발송된다
  - 학부모 전화번호가 수강생마다 따로 저장되어 서로 다른 값으로 남는다
- 어긋나는 데이터
  - 같은 학부모의 전화번호가 수강생별로 불일치
  - 수신 거부가 한 수강생에만 반영되고 다른 수강생에는 발송

### S-5

> 학원 3,000곳, 수강 등록 50만 건 규모

- 명시되지 않은 것
  - 학원당 수강 등록 분포
    - 평균 약 167건이지만 편차가 어느 정도인지
  - 강좌 수 · 수강생 수 · 학부모 수
  - 월 고지서 수가 수강 등록 수와 같은지
  - 이 수치가 초기 seed인지 성능 검증용 기준인지
- 깨지는 시나리오
  - 특정 학원에 수강 등록 5만 건이 몰려 학원 단위 조회가 느려진다
  - 50만 건 생성을 단일 트랜잭션으로 묶어 undo 로그가 커지고 락 대기가 발생한다
- 어긋나는 데이터
  - 생성 작업 중간 실패 시 일부 학원만 고지서가 있는 상태

### S-6

> 애플리케이션 인스턴스 2대 이상으로 운영

- 명시되지 않은 것
  - 스케줄러가 인스턴스마다 도는지, 한 곳에서만 도는지
  - 인스턴스 간 공유 자원 (DB 외에 Redis 등이 허용되는지)
  - 인스턴스 식별자 존재 여부
- 깨지는 시나리오

### S-56

## 3. 숨은 요구사항

### H-1. 고지서 생성 작업은 같은 월에 여러 번 실행돼도 고지서가 중복 생성되지 않아야 한다

- 왜 필요한가: 수동 실행과 자동 실행, 또는 중단 후 재실행이 겹치면 같은 수강 등록 · 같은 월에 고지서가 2장 생긴다
- 유도된 문장: S-41, S-42, S-6

### H-2. 매월 1일 09:00 스케줄과 15분 미확정 · 미납 안내 스케줄은 인스턴스 2대 중 한 곳에서만 실행돼야 한다

- 왜 필요한가: 스케줄러가 인스턴스마다 돌면 생성 · 안내 · 미확정 처리가 전부 2회 발생한다
- 유도된 문장: S-42, S-52, S-59, S-6

### H-3. 웹훅은 같은 messageId로 여러 번 와도 한 번만 반영돼야 한다

- 왜 필요한가: 공급사 재전송이나 네트워크 재시도로 같은 결과가 두 번 오면 이력이 중복되고 SMS 대체가 두 번 나간다
- 유도된 문장: S-23, S-50, S-51

### H-4. send 응답 저장 전에 도착한 웹훅을 잃지 않아야 한다

- 왜 필요한가: 웹훅이 send 응답보다 먼저 도착하면 messageId 매칭에 실패해 고지서가 영원히 미확정으로 남는다
- 유도된 문장: S-18, S-23, S-50

### H-5. 발송을 점유한 인스턴스가 죽으면 점유 건을 일정 시간 후 회수해야 한다

- 왜 필요한가: 점유 상태로 남은 고지서는 어느 인스턴스도 다시 집지 않아 영원히 발송 중이 된다
- 유도된 문장: S-45, S-74

### H-6. 발송 대상 점유는 두 인스턴스가 같은 고지서를 동시에 집지 못하도록 원자적이어야 한다

- 왜 필요한가: 같은 조건의 SELECT를 두 인스턴스가 동시에 읽으면 같은 배치를 두 번 발송한다
- 유도된 문장: S-45, S-6, S-73

### H-7. 초당 100건 한도는 인스턴스 합산으로 지켜지고, 429를 받으면 실패로 확정하지 않고 재시도해야 한다

- 왜 필요한가: 인스턴스별 한도만 두면 합산이 초과하고, 429를 실패로 기록하면 실패 사유 집계가 왜곡된다
- 유도된 문장: S-21, S-46, S-64

### H-8. 발송 금지 시간대는 send 호출 시각 기준으로 판정되고, SMS 대체 · 미납 안내 · 재발송에도 같은 규칙이 적용될지 정해져야 한다

- 왜 필요한가: 20:59에 집어서 21:00 이후에 보내거나, 21:30 웹훅으로 SMS가 즉시 나가면 금지 시간대를 위반한다
- 유도된 문장: S-47, S-51, S-59, S-67

### H-9. 납부일이 해당 월에 없는 경우(29 · 30 · 31일)의 납부기한 산정 규칙이 필요하다

- 왜 필요한가: 납부일 31 · 2월 고지서에서 날짜 생성 예외가 나면 생성 작업 전체가 500으로 실패한다
- 유도된 문장: S-29, S-39

### H-10. 해당 월 수업일이 0일이거나 수강 기간에 포함된 수업일이 0일인 경우의 처리 규칙이 필요하다

- 왜 필요한가: 분모 0으로 나누기가 나거나, 0원 고지서가 생성 · 발송 · 미납 안내 대상이 된다
- 유도된 문장: S-28, S-34, S-57

### H-11. 수강 종료로 종료일이 정해지면 이미 생성된 그 월 고지서와 이후 월 고지서의 처리 규칙이 필요하다

- 왜 필요한가: 종료일 지정 전 전액으로 생성된 고지서가 그대로 남으면 고지 금액과 재계산 금액이 어긋난다
- 유도된 문장: S-30, S-34, S-41

### H-12. PAID 고지서에 다시 납부가 오거나 납부액이 고지 금액을 초과하는 경우의 처리 규칙이 필요하다

- 왜 필요한가: 초과 납부를 허용할지 거부할지 정하지 않으면 납부액 > 고지 금액 데이터가 생긴다
- 유도된 문장: S-55, S-56, S-57

### H-13. 같은 멱등 키에 다른 본문이 오거나, 같은 키가 두 인스턴스에 동시에 들어오는 경우의 처리 규칙이 필요하다

- 왜 필요한가: 키만 검사하면 다른 금액 요청에 첫 결과를 돌려주고, 동시 요청은 둘 다 insert 된다
- 유도된 문장: S-58, S-6

### H-14. 원장의 수동 금액 수정과 자동 재계산(종료일 변경 · 형제 할인 변경)이 겹칠 때 우선순위가 필요하다

- 왜 필요한가: 우선순위 없이 재계산하면 원장이 수정한 값이 사라진다
- 유도된 문장: S-38, S-34, S-36, S-30

### H-15. 이미 발송 · 납부된 고지서의 금액 수정 시 재발송 여부와 납부 상태 재판정 규칙이 필요하다

- 왜 필요한가: 발송 후 금액을 바꾸면 학부모는 옛 금액을 보고, PAID가 PARTIAL로 되돌아갈 수 있다
- 유도된 문장: S-38, S-50, S-57

### H-16. 형제를 판별할 기준 데이터(학부모 · 보호자 연결)가 도메인에 있어야 한다 (확인 필요)

- 왜 필요한가: 원문 엔티티 목록(강좌 · 수강생 · 수강 등록)에 학부모가 없어 형제 판별 근거가 없다
- 유도된 문장: S-3, S-36, S-37
- (확인 필요) 이유: 학부모를 별도 엔티티로 둘지, 수강생에 학부모 전화번호만 둘지에 따라 필요한 데이터가 다르다

### H-17. 학부모의 수신 거부 상태를 저장하고 변경할 수 있어야 한다

- 왜 필요한가: 수신 거부 데이터가 없으면 제외할 수 없고, 변경 API가 없으면 seed로만 검증된다
- 유도된 문장: S-48

### H-18. 학원에 유료 · 무료 플랜 속성이 있어야 한다

- 왜 필요한가: SMS 대체 발송 조건을 판정할 데이터가 원문 엔티티에 없다
- 유도된 문장: S-51

### H-19. SMS 대체 발송의 결과 확정 방식(웹훅 · 동기 응답)이 정해져야 한다

- 왜 필요한가: SMS 결과 경로가 없으면 대체 발송 건이 영원히 미확정으로 남는다
- 유도된 문장: S-20, S-51, S-52

### H-20. 미확정 처리 후 늦게 도착한 웹훅의 반영 규칙과, 미확정 건의 재발송 가능 여부가 정해져야 한다

- 왜 필요한가: 미확정 건을 재발송한 뒤 원래 웹훅이 DELIVERED로 오면 중복 발송이 된다
- 유도된 문장: S-52, S-50, S-67

### H-21. 미납 안내는 같은 고지서 · 같은 시점(3일 · 7일)에 한 번만 발송돼야 한다

- 왜 필요한가: 스케줄러가 하루 여러 번 돌거나 두 인스턴스에서 돌면 같은 안내가 반복된다
- 유도된 문장: S-59, S-6

### H-22. 미납 안내 대상 판정에 PARTIAL 포함 여부와, 안내 시점 전에 납부 완료된 건의 제외가 정해져야 한다

- 왜 필요한가: 정의 없이 구현하면 부분 납부 학부모에게 안내가 가거나, 이미 낸 학부모에게 안내가 간다
- 유도된 문장: S-59, S-57

### H-23. 정원 검사와 등록 insert는 동시 요청에서도 원자적이어야 한다

- 왜 필요한가: count 후 insert 사이에 다른 요청이 끼면 정원을 초과한다
- 유도된 문장: S-31, S-71, S-6

### H-24. 기간 중복 판정에서 종료일 null(무기한)과 경계일(종료일 = 시작일) 처리가 정해져야 한다

- 왜 필요한가: null 비교를 빠뜨리면 무기한 등록과 겹치는 등록이 통과한다
- 유도된 문장: S-29, S-32

### H-25. 잘못된 입력(납부일 0 · 32, 음수 원비, 정원 0, 빈 요일, 잘못된 헤더)은 4xx로 응답해야 한다

- 왜 필요한가: VO 생성자 예외나 날짜 파싱 예외가 그대로 새면 500이 된다
- 유도된 문장: S-13, S-28, S-29

### H-26. 수업 요일 목록에 같은 요일이 중복되면 거부하거나 정규화해야 한다

- 왜 필요한가: `[MON, MON]`이 저장되면 수업일이 2배로 계산돼 원비가 틀어진다
- 유도된 문장: S-28, S-34

### H-27. 학원 헤더 누락 · 존재하지 않는 학원 · 다른 학원 리소스 접근의 응답 코드가 각각 정해져야 한다

- 왜 필요한가: 구분하지 않으면 존재 여부가 노출되거나 클라이언트가 원인을 알 수 없다
- 유도된 문장: S-13

### H-28. 재발송은 새 messageId를 발급하고 기존 발송 이력을 보존해야 한다

- 왜 필요한가: messageId를 덮어쓰면 첫 발송 웹훅이 매칭되지 않고 이력이 사라진다
- 유도된 문장: S-67, S-65, S-50

### H-29. 로그에 고지서 ID · messageId · 작업 ID를 상관 식별자로 남겨야 한다

- 왜 필요한가: 웹훅 처리 로그에 고지서 ID가 없으면 로그만으로 이력을 재구성할 수 없다
- 유도된 문장: S-66, S-65

### H-30. 진행 현황 집계는 50만 건에서 1초 이내가 되도록 실시간 count 외의 전략이 필요하다 (확인 필요)

- 왜 필요한가: `GROUP BY status` 실시간 count가 50만 건에서 1초를 넘길 수 있다
- 유도된 문장: S-62, S-63
- (확인 필요) 이유: 인덱스가 있는 status 컬럼의 count는 50만 건에서 1초 이내일 수도 있다. 실측 없이 단정할 수 없다

### H-31. "발송 작업"을 식별하고 상태를 갖는 개념이 필요하다 (확인 필요)

- 왜 필요한가: 진행 현황 · 실패 건 조회 · 재발송이 모두 "작업" 단위를 전제하는데 원문에 작업의 식별자 · 상태가 없다
- 유도된 문장: S-41, S-62, S-64, S-67
- (확인 필요) 이유: 작업을 별도 엔티티로 두지 않고 "학원 + 월"로 식별하는 해석도 가능하다

### H-32. 고지서의 발송 상태와 납부 상태는 별도 축으로 관리돼야 한다

- 왜 필요한가: 발송 실패 + 납부 완료 같은 조합이 존재하므로 한 enum으로는 표현이 안 된다
- 유도된 문장: S-50, S-52, S-57

### H-33. 시간대(KST) 기준을 고정해야 한다

- 왜 필요한가: 서버가 UTC로 돌면 09:00 · 21:00 · 자정 기준이 전부 어긋난다
- 유도된 문장: S-42, S-47, S-59

### H-34. 429 · 타임아웃 · 웹훅 실패 코드를 구분해 실패 사유로 기록하고, 재시도 상한이 있어야 한다

- 왜 필요한가: 사유별 필터가 동작해야 하고, 상한이 없으면 FAILED_ETC 반복 건이 무한 재시도된다
- 유도된 문장: S-21, S-24, S-64, S-67

### H-35. 가짜 클라이언트는 인스턴스 2대 환경에서도 실제처럼 웹훅을 전달해야 한다

- 왜 필요한가: 내부 메서드 호출로 웹훅을 흘리면 send를 호출한 인스턴스만 결과를 받아 2대 환경 검증이 실제와 다르다
- 유도된 문장: S-25, S-23, S-73

### H-36. 다른 학원의 리소스에 접근했을 때 응답이 정보 노출 없이 일관돼야 한다

- 왜 필요한가: 403과 404가 섞이면 다른 학원 리소스의 존재 여부가 드러난다
- 유도된 문장: S-13

### H-37. 고지서 생성 후 등록된 수강이 그 월 고지서를 받을지 정해져야 한다

- 왜 필요한가: 1일 09:00 이후 등록된 수강은 그 월 고지서가 없어 납부 관리에서 빠진다
- 유도된 문장: S-41, S-42, S-29

### H-38. 산정 결과가 0원인 고지서의 발송 · 납부 상태 · 미납 안내 규칙이 필요하다

- 왜 필요한가: 0원 고지서가 UNPAID로 남으면 발송되고 미납 안내까지 나간다
- 유도된 문장: S-34, S-38, S-57, S-59

### H-39. 발송에 필요한 학부모 전화번호가 도메인에 있어야 한다

- 왜 필요한가: `send(messageId, phone, ...)`에 넣을 전화번호 필드가 원문 엔티티 목록에 없다
- 유도된 문장: S-18, S-20, S-3

### H-40. 생성 대상이 0건인 작업의 결과 처리가 정해져야 한다

- 왜 필요한가: 대상 0건일 때 작업을 실패로 볼지 완료로 볼지 없으면 진행 현황이 비어 보인다
- 유도된 문장: S-41, S-62

### H-41. 발송 전 · 수신 거부 제외 · 미확정 고지서에 납부가 들어오는 경우의 허용 여부가 필요하다

- 왜 필요한가: 발송 전 PAID가 된 고지서가 이후 발송되면 학부모가 이미 낸 고지서를 받는다
- 유도된 문장: S-55, S-48, S-52

### C-1. 고지서의 단위를 수강 등록 1건으로 하는가, 학부모 · 수강생 단위로 합산하는가

- 관련: S-3 · S-41 · S-57 · H-32
- 선택지
  1. A: 수강 등록 1건 · 1개월 = 고지서 1장
     - 장점: 원비 산정 · 금액 수정 · 납부 상태가 수강 등록에 1:1로 대응해 단순하다
     - 단점: 자녀 · 강좌가 여럿인 학부모는 같은 날 여러 장을 받는다
  2. B: 학부모 1명 · 1개월 = 고지서 1장, 안에 수강 등록별 항목
     - 장점: 학부모가 받는 알림톡이 1건이고 형제 할인 표현이 자연스럽다
     - 단점: 항목별 금액 수정 · 부분 납부 배분 · 학부모 모델이 필수가 되어 범위가 커진다
  3. C: 수강생 1명 · 1개월 = 고지서 1장
     - 장점: 학부모 모델 없이도 수강생 단위 합산이 가능하다
     - 단점: 형제 할인은 여전히 학부모 연결이 필요하고, A보다 복잡하며 B의 장점은 얻지 못한다

### C-2. "해당 월 유효 수강 등록"의 경계를 어떻게 정하는가

  3. C: 작업 실행 시점에 종료되지 않은 등록만 (실행일 기준 활성)
     - 장점: 조회 조건이 가장 단순하다

### C-8. 납부기한이 어느 월의 납부일인가

### C-11. 고지서 발송 상태값과 전이

- 관련: S-50 · S-52 · S-24 · S-48 · H-32 · H-31
- 선택지
  1. A: 최소 세트
     - `READY`(생성) → `SENDING`(점유) → `REQUESTED`(send 응답) → `DELIVERED` / `FAILED` / `UNCONFIRMED`
     - `EXCLUDED`(수신 거부)는 `READY`에서 분기
     - 장점: 상태 수가 적어 집계 · 테스트가 짧다
     - 단점: 실패 사유 · 채널이 상태에 없어 별도 컬럼이 필요하다
  2. B: 채널 · 사유를 상태에 포함
     - `FAILED_NOT_KAKAO_USER` · `FAILED_ETC` · `SMS_REQUESTED` · `SMS_DELIVERED` 등
     - 장점: 상태만 보면 전부 알 수 있다
     - 단점: 채널 추가 시 상태가 늘어나고(S-53) 집계 그룹이 흩어진다
  3. C: 고지서 상태는 `READY` · `SENT` · `FAILED` · `UNCONFIRMED`로 두고, 시도별 상세는 발송 이력에만 기록
     - 장점: 고지서와 발송 시도가 분리되어 재발송 표현이 자연스럽다
     - 단점: 진행 현황 집계가 두 테이블에 걸친다

### C-12. 미확정 건에 늦게 온 웹훅을 반영하는가, 미확정 건을 재발송할 수 있는가

### C-13. 발송 작업(Job)의 단위와 상태

### C-14. 진행 현황 집계 전략 (50만 건 1초 이내)

### C-15. "초당 처리량"의 정의

### C-16. 인스턴스 2대 중복 발송 방지 — 발송 대상 점유 방식

- 관련: S-45 · S-6 · S-73 · S-74 · H-5 · H-6
- 선택지
  1. A: `SELECT ... FOR UPDATE SKIP LOCKED`로 배치를 잠그고 같은 트랜잭션에서 상태 갱신
     - 장점: MySQL 8 기능으로 추가 인프라 없이 겹침이 없다
     - 단점: 트랜잭션 안에서 외부 호출을 하면 잠금이 길어지므로 점유와 발송을 분리해야 한다
  2. B: `UPDATE ... SET owner, leased_until WHERE status = READY LIMIT n` 후 owner로 재조회 (클레임)
     - 장점: 잠금 시간이 짧고 lease로 회수 규칙이 데이터에 남는다
     - 단점: MySQL의 `UPDATE ... LIMIT`는 정렬 조건이 제한되어 배치 선택 순서를 통제하기 어렵다
  3. C: 고지서 ID를 인스턴스 수로 나눠 파티션 (ID mod N = 인스턴스 번호)
     - 장점: 잠금 경합이 전혀 없다
     - 단점: 인스턴스가 죽으면 그 파티션이 멈추고, N 변경 시 재배정이 필요하다

### C-17. 점유 회수 기준 시간 (죽은 인스턴스의 건)

- 관련: S-74 · H-5 · S-52
- 선택지
  1. A: 점유 후 5분 지나면 `READY`로 회수
     - 장점: 15분 미확정보다 짧아 회수와 미확정이 겹치지 않는다

  2. B: 점유 후 15분 (미확정과 동일)

### C-19. 429 · 타임아웃 재시도 상한과 백오프, 호출 타임아웃 값

- 선택지

  3. C: 재시도 상한 5회 · 고정 간격 1초, 호출 타임아웃 500ms
     - 장점: 지연 300ms 상한에 맞춘 빠른 실패 판정
     - 단점: 300ms 근처 응답이 타임아웃으로 새어 실패율이 높아진다

  3. C: 같은 키면 409 반환 (재시도 클라이언트가 GET으로 확인)

### C-23. 부분 납부에서 초과 납부 처리

- 선택지
  1. A: 잔액 초과 요청은 4xx 거부
     - 장점: 납부액 ≤ 고지 금액 불변식이 유지된다
     - 단점: 금액 수정으로 고지 금액이 내려간 뒤에는 불변식이 이미 깨질 수 있어 별도 규칙이 필요하다
  2. B: 허용하고 초과분을 기록 (상태는 `PAID`, 초과 금액 컬럼)
     - 장점: 실제 입금을 그대로 반영한다
     - 단점: 환불 · 이월 개념이 없어 초과분이 표시만 된다
  3. C: 잔액만큼만 반영하고 나머지는 응답으로 알린다

### C-24. 수동 금액 수정과 자동 재계산이 겹칠 때 우선순위

- 관련: S-38 · S-30 · S-36 · H-14
- 선택지
  1. A: 수동 수정이 항상 우선, 재계산은 수정 표시가 있는 고지서를 건너뛴다
     - 장점: 원장의 의도가 사라지지 않는다
     - 단점: 종료일 변경으로 금액이 줄어야 할 때 반영이 안 된다
  2. B: 재계산이 덮어쓰고 이전 수동 수정을 이력에 남긴다
     - 장점: 항상 규칙대로의 금액이다
     - 단점: 원장이 수정을 다시 해야 하고 알림이 없으면 눈치채지 못한다
  3. C: 수동 수정된 고지서에는 종료일 변경 등 재계산 유발 요청을 거부한다
     - 장점: 충돌 자체가 없다
     - 단점: 수강 종료가 막혀 운영이 불편하다

### C-25. 금액 수정의 대상 — 생성 전 예약인가, 생성 후 고지서인가

### C-26. 발송 · 납부 후 금액 수정 허용 범위

### C-27. 미납 안내 대상 — PARTIAL 포함 여부와 "경과 3일"의 계산

### C-31. 식별자 형식 (엔티티 ID · messageId)

- 선택지

     - 단점: MySQL에 시퀀스가 없어 TABLE 전략의 락 경합을 감수해야 한다

### C-37. 수신 거부 학부모의 고지서 — 생성하지 않는가, 생성하되 발송만 제외하는가

  2. B: 포함 (연체일수 0으로 목록 끝에 노출)
     - 장점: 기준일 시점 안 낸 건이 전부 보인다
     - 단점: 아직 기한이 안 지난 건이 "미납"으로 표시된다

### C-53. 수강 종료 재계산 결과가 이미 납부액보다 작을 때

- 관련: S-30 · S-57 · C-23 · C-26 · C-40
- 선택지
  1. A: 금액 하한을 납부액으로 고정 (재계산 결과 < 납부액이면 납부액으로 설정, 이력에 사유 기록)
     - 장점: paidAmount ≤ totalAmount 불변식이 유지된다
     - 단점: 규칙상 금액과 달라져 설명이 필요하다
  2. B: 재계산 결과 그대로 반영 (납부액 초과 허용)
     - 장점: 규칙상 금액 그대로다
     - 단점: 불변식이 깨지고 환불 개념이 필요해진다

### C-54. 발송 시점에 이미 PAID인 고지서를 발송하는가

- 관련: S-45 · S-56 · C-37 · C-16
- 선택지
  1. A: 발송한다 (발송 축과 납부 축 독립)
     - 장점: 클레임 조건이 send_status 하나로 단순하다
     - 단점: 이미 낸 학부모가 고지서를 받는다
  2. B: 클레임 시 PAID 제외
     - 장점: 불필요한 알림이 없다
     - 단점: 클레임 조건에 납부 축이 섞여 인덱스·테스트가 늘어난다

### C-55. 재발송 접수 후 이전 시도의 늦은 웹훅이 오면 고지서 상태를 갱신하는가

- 관련: S-52 · S-67 · C-12
- 선택지
  1. A: 시도(attempt)만 확정, 고지서 상태는 최신 시도의 결과로만 갱신
     - 장점: 고지서 상태의 기준이 "최신 시도" 하나로 고정된다
     - 단점: 이전 시도가 실제 도착했어도 고지서에는 반영되지 않는다
  2. B: 어느 시도든 DELIVERED가 오면 고지서를 SENT로
     - 장점: 도착 사실이 우선된다
     - 단점: 재발송 진행 중 상태가 되돌아가 전이 규칙이 복잡해진다

### 5.1 검증 요구가 확인하려는 역량

1. 정원 동시 등록 테스트 — 근거: S-71, S-31
   - DB 수준 동시성 제어(잠금 · 원자 갱신)를 설계하고 그것을 테스트로 증명하는 능력
   - 스레드 풀로 동시 요청을 만들고 결과 건수를 검증하는 테스트 작성 능력
2. 원비 산정 파라미터 테스트 — 근거: S-72, S-34, S-35
   - 계산 규칙을 도메인 객체로 분리해 순수 단위 테스트가 가능하게 만드는 능력
   - 시작 월 · 종료 월 · 같은 월 · 수업일 0 · 절사 · 할인 등 경계값을 스스로 열거하는 능력
3. 고지서 5만 건 · 인스턴스 2대 실행 결과 — 근거: S-73, S-45, S-46
   - 인스턴스 간 중복 없는 작업 분배(점유 · 잠금)
   - 합산 rate limit 구현
   - 소요 시간 · 중복 · 초당 요청 수를 측정하고 관측하는 능력
4. 실행 중 인스턴스 1대 종료 시 결과 — 근거: S-74, S-45
   - 점유 상태 회수(lease) · 재시작 후 재개 · 중복 방지의 조합
   - 장애를 실제로 일으키고 결과를 설명하는 검증 태도
5. 주요 쿼리 실행 계획과 인덱스 설계 근거 — 근거: S-75, S-63, S-60
   - 50만 건 규모에서 발송 대상 조회 · 집계 · 정렬 쿼리의 인덱스 설계
   - EXPLAIN을 읽고 근거로 제시하는 능력
6. README 항목 (가정과 근거 · 미구현 항목과 구현 방향) — 근거: S-78, S-15, S-8
   - 모호한 요구를 스스로 정의하고 근거를 남기는 능력
   - 범위를 잘라내고 우선순위를 설명하는 능력
7. 50만 건 생성 소요 시간 — 근거: S-43
   - 대량 insert 전략(배치 · ID 생성 전략)에 대한 이해

### 5.2 평가 비중이 클 것 같은 순서

1. 인스턴스 2대 환경에서 중복 없는 발송과 합산 rate limit (확인 필요)
   - 이유: 개요(S-6) · 발송(S-45 · S-46) · 검증(S-73 · S-74)에서 네 번 반복된다
   - 이유: 검증 요구 5개 중 2개가 여기에 걸린다
2. 도메인 정합성 — 정원 동시성 · 원비 산정 (확인 필요)
   - 이유: 검증 요구에 테스트 항목으로 직접 명시됐다 (S-71 · S-72)
   - 이유: 예시 값(S-35)이 주어져 정답 대조가 즉시 가능하다
3. 구현 범위와 우선순위 판단, 가정의 근거 (확인 필요)
   - 이유: "평가에 포함"이라고 유일하게 명시된 항목이다 (S-8)
   - 이유: README 요구 항목에 "가정과 근거" · "미구현 항목과 구현 방향"이 있다 (S-78)
4. 웹훅 기반 상태 확정 · 미확정 · SMS 대체 (확인 필요)
   - 이유: 외부 연동 절 전체(S-21~S-25)와 발송 결과 절(S-50~S-53)이 이 흐름을 위한 것이다
   - 이유: 비동기 · 순서 역전 · 중복 수신을 다루는 설계 역량이 드러난다
5. 납부 멱등성과 부분 납부 (확인 필요)
   - 이유: "멱등성 보장"이 명시된 유일한 API다 (S-58)
   - 이유: 정합성 테스트로 바로 판별된다
6. 운영 조회 · 인덱스 설계 (확인 필요)
   - 이유: 1초 이내(S-63) 수치와 실행 계획 제출(S-75)이 요구됐다
7. 미납 안내 · 미납 목록 · 이력 · 로그 추적 (확인 필요)
   - 이유: 필수 요구이지만 검증 요구에 직접 언급이 없다
8. 선택 요구 — 학원별 발송 시각 (확인 필요)
   - 이유: "선택"으로 분리됐다 (S-68)

### 5.3 5시간 안에 다 못 할 때

**포기하면 감점이 큰 것**
1. 인스턴스 2대에서 중복 없는 발송 (S-45 · S-73 · S-74)
   - 검증 요구 2개가 직접 걸려 있다
2. 합산 초당 100건 제한과 429 처리 (S-46 · S-21)
   - 5만 건 검증 결과의 "초당 요청 수" 항목이다
3. 정원 동시 등록 테스트 (S-71 · S-31)
   - 테스트 하나로 판별되고 실패 시 정합성 전체가 의심받는다
4. 원비 산정 파라미터 테스트와 예시 값 일치 (S-72 · S-35)
   - 정답이 주어져 있어 틀리면 바로 드러난다
5. 학원 헤더 식별과 타 학원 접근 거부 (S-13)
   - 기술 조건이라 모든 API의 전제다
6. Docker Compose 실행과 README 실행 방법 (S-11 · S-78)
   - 실행이 안 되면 나머지가 평가되지 않는다
7. 가정과 근거 · 미구현 항목과 구현 방향 (S-15 · S-78 · S-8)
   - 미구현 자체보다 미구현을 설명하지 않는 것이 감점이다
8. 고지서 생성 작업과 자동 스케줄 (S-41 · S-42)
   - 발송 검증의 입력 데이터가 여기서 나온다

**설계안으로 대체해도 되는 것**
1. 학원별 발송 시각 설정 (S-69)
   - 선택 요구
2. 미납 안내 3일 · 7일 발송 (S-59)
   - 스케줄 · 1회 보장 설계를 문서로 남기고 구현은 후순위
3. SMS 대체 발송 (S-51)
   - 채널 추상화 지점(S-53)과 함께 설계로 설명 가능
4. 발송 후 15분 미확정 처리 (S-52)
   - 스캐너 설계와 상태 전이를 문서로, 구현은 시간 여유 시
5. 로그로 동일 추적 (S-66)
   - MDC · 식별자 로깅 규칙을 문서로 남기고 최소 로그만
6. 실패 건 사유별 필터 · 재발송 API (S-64 · S-67)
   - 재발송 규칙(새 messageId · 이력 보존)을 설계로 남기고 단건 재발송만 구현하는 절충 가능
7. 50만 건 생성 실측 (S-43)
   - 5만 건 실측 + 외삽 근거로 대체 (C-49)
8. 기준일 시점 미납 목록의 과거 기준일 정확성 (S-60)
   - 현재 상태 기준으로 구현하고 과거 기준일 한계를 문서로
9. 형제 할인의 소급 · 재계산 (S-36)
   - 생성 시 고정으로 구현하고 재계산 규칙을 설계로
