# /design — F0 설계

- 과제 원문으로 설계 문서와 task_list를 만든다
- 사용자 결정을 받아 반영한다
- 설계 점검까지 돌린다

이 스킬은 메인 세션에서 아래 순서를 **그대로** 실행한다.

- 순서를 바꾸거나 단계를 건너뛰지 않는다
- `🛑 멈춤`이 나오면 그 자리에서 사용자에게 보고하고 응답을 기다린다

## 0. 사전 확인

- `docs/design/00-assignment.md`의 "원문" 아래가 비어 있으면
  - → 🛑 멈춤: "원문을 붙여넣어 주세요"
- 작업 트리에 커밋 안 된 변경이 있으면
  - → 🛑 멈춤: 변경 목록을 보여주고 처리 방법을 묻는다
- `main`에서 `feature/design` 브랜치를 만든다 (이미 있으면 그 브랜치로 이동)
- `docs/task_list.md` 시간 계획의 시작 시각을 현재 시각으로 적는다
- 원문을 커밋한다: `docs: 과제 원문 추가` → task_list T0-1 체크

## 1. 초안 작성

- `doc-writer`를 호출한다
  - 지시: "F0 설계 초안을 작성하라. `01` → `02` → `03` → `task_list` 순서"
- 끝나면 네 문서를 직접 훑는다
  - 템플릿 자리표시(`{기능명}`, 빈 표 행)가 남았는지 확인한다

## 2. 결정 받기

- `01` §5의 `D-x` 중 `사용자 결정 필요`인 항목을 모은다
- 🛑 멈춤: 아래 형식으로 보고하고 결정을 받는다
  - 가능하면 AskUserQuestion으로 항목별 선택지를 준다

```
## 설계 초안 완료
- FR n / NFR n / SUB n / TC n / API n / 기능 F n개
- 원문 중 옮기지 못한 문장: …

## 결정이 필요한 항목
### D-1. 쟁점
- A (추천): … — 장단점
- B: … — 장단점
```

- 결정이 없으면 이 단계는 보고만 하고 넘어간다

## 3. 결정 반영

- `doc-writer`를 호출해 결정을 반영한다
  - `D-x`의 결정 · 근거 칸을 채운다
  - `(D-x 대기)` 표시를 지운다
  - 추천안과 다르게 정해진 행은 고친다

## 4. 설계 점검

- `verifier`를 **설계 점검 모드**로 호출한다
- 높음 지적이 있으면 `doc-writer`로 고친다
  - 고친 뒤 `verifier`를 한 번 더 돌린다 (최대 2회)
- 아래 중 하나면 → 🛑 멈춤: 지적과 선택지를 보고한다
  - 2회 뒤에도 높음이 남는다
  - 고치려면 새 결정이 필요하다

## 5. 커밋

task_list의 F0 작업 줄 문장으로 문서별 커밋을 만든다.
각 커밋에 해당 체크박스 갱신을 포함한다.

- `docs: 요구사항 구체화 및 테스트 케이스 작성` — `01`
- `docs: 도메인 모델 및 ERD 작성` — `02`
- `docs: API 명세 및 에러 코드 작성` — `03`
- `docs: 작업 목록 작성` — `task_list` (시간 계획의 F0 실제 종료 시각 포함)

## 6. 마무리

🛑 멈춤: 아래를 보고하고 머지 여부를 묻는다.

```
## F0 설계 완료 (소요 hh:mm / 목표 1:00)
- 문서: FR n / NFR n / TC n / API n / ErrorCode n
- 결정: D-1 …, D-2 …
- 설계 점검: 높음 0 / 중간 n / 낮음 n (남긴 지적 목록)
- 기능 순서: F1 … → F2 … → …

PR을 올릴까요? (push → PR 생성. 머지는 GitHub에서 직접)
```
